# terrain6 树加载队首阻塞修复（2026-11-07）

本轮基于 `5519fd1`（此前树回访缓存与顶点循环优化）。修复的是可复现的加载正确性缺陷，不是另一个小幅性能计时优化。

## 缺陷证据

terrain6 在显示预算失败后进入受限视域恢复，`V6IslandView` 只请求与真实视域相交的地面区块。树调度为宽树冠保留两格区块边距，因此可能额外请求地面没有驻留的边缘树区块。

旧 `V6TreeStreaming` 只有一个正在构造/上传的任务槽，按距离选最近块。`V6TreeView.publish` 会拒绝没有地面的树，但旧调度一直重试这个队首，无法继续后面的已就绪块。

修改前使用 seed 42173 的两个真实树身份、正式调度/视图/上传代码及 Cocos 调用替身复现：

- 视域为 x=130..142、z=32..128；受限地面驻留 x 区块 8，而树边距还包括区块 7。
- `t422` 位于 (114,48)，属于 7:3，地面没有驻留；它按区块中心距离排在前面。
- `t992` 位于 (141,120)，属于 8:7，地面已就绪，却被前者挡住。
- 推进 1000 次后，仍没有树发布，pending 一直为 7:3，loading 一直为 true，GPU Mesh 创建数为 0。

这证明了该调度条件下的永久阻塞，不代表用户手机上所有加载卡顿都由它造成。

## 修复

`V6TreeView` 向调度器提供现有的地面可见性查询。调度只为已有地面的候选块分配任务槽；失去地面的暂存任务取消，让其他已就绪块继续。

- 树和 terrain6 地面均按 16×16 划块。候选筛选按块中心查询，避免逐树重复扫描；正式地面可见性是整个区块的状态，保存树位于整数格，实际偏移树脚仍在同一块内。
- **没有放宽发布或交互条件**：上传前仍逐个检查实际树脚；远景树仍须等细地面就绪才能被采集。原有遮挡和禁止穿透选择行为保留。
- 树的 loading 只表示当前有地面候选中的未完任务。不再为可能永远不加载的边缘地面显示永久树加载；全局地形准备/细化仍由原 `TownView.loading` 的地形分支表示。
- 地面以后就绪会在下一次调度自动发现，不需要重新加载存档或重新 sync 树列表。
- 原来已发布的完整树几何在地面临时变脏或 LOD 切换时仍保留；本轮没有改为整片闪退重建。未发布 CPU/GPU 半成品按既有取消路径释放。
- 不增加缓存、常驻预算、地图尺寸或新玩法，不修改保存格式及树身份；v5 路径不变。

## 修改后对照与验证

同一 1000 次推进场景，现在 `t992` 发布，7:3 不占用任务槽，树 loading 为 false。随后让 7:3 的地面发布，无需重新 sync，`t422` 自动加载。修改前后最终两棵树的 Float64 网格、精确拾取及正式上传分片指纹完全一致，保存状态逐字节不变，模拟 Mesh 均恰好销毁一次，销毁后缓存记账为 0。

复现脚本：`scripts/reproduce-v6-tree-ground.cjs`。
