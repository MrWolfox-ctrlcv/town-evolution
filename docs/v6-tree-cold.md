# terrain6 首次进入树区的 CPU 构造（2026-11-07）

基于已交付整合源码 b8a8f7f 加上一轮树回访缓存（本地冻结点 697948f）。本轮只调整 `V6TreeGeometry.ts` 的逐顶点位置变换循环；不改变地图、材质、树外观、保存身份、成长、LOD、拾取或上传预算。

## 热点和最小改动

真实 seed 42173 的 `7:3` 密集区有 67 棵保存树，近景批次含 60360 个顶点、21928 个三角形。初步 CPU 采样发现逐顶点构造与垃圾回收是主要热点，树脚高度查询占比很小。

原循环为每个顶点分配临时 `[x,y,z]` 数组，再分别循环三个轴执行 F32 舍入和边界更新。本轮改用三个局部数值和显式边界更新，每棵树的顶点顺序、乘加结合顺序、`Math.fround`、法线运算均不变。密集近景批次因此不再创建这 60360 个临时三元数组。这是源码层面的分配次数减少，不是实测堆内存减少量。

没有新缓存、池、持久数组或引用，没有更改上一轮的 8 MiB / 32 项非活跃树 CPU 预算，也没有增加 GPU 常驻。已有逐树分帧构造、离场取消、地面就绪检查、隐藏上传、原子发布和销毁路径保持不变。

## 同条件对照

脚本 `scripts/benchmark-v6-tree-cold.cjs` 使用同一份真实保存状态与树脚高程源，对修改前后每次都新建树批次，不命中回访缓存。每版先预热 3 次，再执行 21 组 AB/BA 顺序交错的配对测量，不显式调用 GC。

测的是**已加载模板/JIT 条件下，首次进入一个尚未构造的树区所需的 CPU 批次构造**。它不是冷进程启动、全岛加载、Cocos 帧时、GPU 或手机测试；不包含 GPU 上传。

记录位于 `benchmarks/v6-tree-cold-20261107.json`：

- 成熟近景 67 棵：中位 **16.24 → 14.65 ms**，本次样本约下降 9.8%。21 对中 13 对更快，单次波动明显，不能承诺每次均提速。
- 混合成长近景 67 棵：中位 **11.07 → 9.96 ms**，本次约下降 10.1%，21 对中 16 对更快。成长阶段为合成覆盖场景，位置来自同一真实区块。
- 成熟远景 67 棵：**1.58 → 1.56 ms**，差异约 1.2%，应视为无明显收益。
- 初次完整批次（包含模板准备、变换和拾取构造）的单次计时另列为 `firstBatchMsIncludingTemplateSetup`，不是模板准备单项计时，也不据此宣称冷启动已稳定改善。

## 几何、拾取与保存验证

新增 10 组修改前金标准覆盖真实密集近/远景、混合成长、空批次、另外三种种子及全部成长阶段。按 Float64 字节计算位置、法线、颜色、索引和边界指纹，保留有符号零；同时比较所有树的真实身份、树脚、拾取边界、每树九条射线，以及正式上传分片的属性和字节数。

10 组指纹全部相同。正式基准的保存状态逐字节不变。连同上一轮缓存、树脚高程与反馈回归，最终定向 33/33 通过。独立复核重新对照修改前编译输出，确认全部金标准一致，且生产编译结果仅 `V6TreeGeometry.js` 改变。

domain 与官方 Cocos 类型、项目结构、架构、222 项素材检查通过。没有重复刚完成的全仓长测：上一轮完整检查及其 5 项引擎路径补测的记录继续保留；本轮不把旧聚合结果冒充在新代码上全量重跑。

## 未解决范围

仍须进行树顶点变换、法线处理、精确拾取构造、模板首次编译和 GPU 上传；超大树批次也仍可能跨多帧加载。此改动没有证明可避免全部卡顿。WebGL、实际 GPU、Android 和手机未测试，未构建新网页预览，未推送或部署。

复现：将 `V6_TREE_COLD_BASELINE_BUILD` 指向修改前 697948f 检查点的 `.domain-build`，编译当前版本后执行 `node scripts/benchmark-v6-tree-cold.cjs`。`V6_TREE_COLD_OUTPUT` 可指定输出 JSON；正常比较不需要重新生成金标准。
